# bouncer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A skill plus bundled Node CLI that checks every on-chain action an agent wants to take against a policy
file (time window, contracts, recipients, approvals, spend per tx and per day), judging the transaction's real
call trace on Pharos mainnet, answers ALLOW or DENY with the deciding rule, sends only on ALLOW, and keeps a
hash-chained audit log.

**Architecture:** A request becomes one unsigned tx. `gate()` runs it through `debug_traceCall` (callTracer,
withLog) from the policy's wallet at one block, reads the trace into facts (called contracts with their call
path, PROS and token outflows, receivers, approvals, revert), then runs the rules in a fixed order; the first
failure decides. Every decision goes to `audit.jsonl`. `send` gates again at send time and signs only that exact
tx. Chain access goes through one `Chain` interface with tapes, as in 15-onego, so tests replay real mainnet
answers offline.

**Tech Stack:** TypeScript (NodeNext, ES2022, strict), viem 2.57.7, node:test, esbuild 0.28.2 bundle into
`skill/bouncer/scripts/bouncer.mjs`. Same versions as 15-onego.

**Spec:** `docs/superpowers/specs/2026-11-04-bouncer-design.md`

## Global Constraints

- Folder `16-bouncer`, standalone package like `15-onego` (own package.json and lock, tsconfig extends `../tsconfig.base.json`, not in root workspaces). Install only on drive D: `npm install --cache D:\.claude\pyCharm\!AIpharosVILLABAJO\.npm-cache`.
- Chain id 1672, RPC `https://rpc.pharos.xyz`; on `-32011` or HTTP 429 wait 1.5 s and retry, up to 8 times. Mainnet only.
- Data folder: `BOUNCER_HOME`, else `%APPDATA%\bouncer` / `~/.config/bouncer`. Holds `policy.json`, `.env` (`PRIVATE_KEY=0x...`), `audit.jsonl`, `audit.lock`. The key is never printed, never taken on the command line.
- All address comparisons lower-cased. Amounts are decimal strings parsed with viem `parseUnits`; more decimals than the asset has, zero, negative or exponent notation is bad input (exit 2), never rounded.
- Rule order and ids exactly: `policy`, `time_window`, `simulation`, `contracts`, `recipients`, `approvals`, `spend.per_tx`, `spend.per_day`. The Claude's-calls list in the spec ("Details settled while writing this up") is binding.
- Exit codes: 0 allow or sent, 3 deny, 2 bad input or no key, 1 network or other error. A network error is never an ALLOW and is logged as `error`.
- Gas: limit = estimate x 12 / 10; maxFee = gasPrice x 2; priority fee as in 15-onego `send.ts`. Gas is not in spend caps; `simulation` denies when value + limit x maxFee > balance.
- Code, comments, docs, CLI text in English, no em dashes. Non-generic names, conversational comments (see 15-onego). Commits as vi11abajo, human-sounding messages, no co-author, commit AND push after every task.
- Claude never runs `bouncer send` against mainnet: the user does (Task 11).

## Review Focus

- Mixed-case addresses in the policy vs lower-case in the trace: must match. Test in Task 3 (`parsePolicy` normalizes) and Task 5.
- RPC dies mid-gate (trace returns error or null, `eth_getCode` throws): exit 1, audit line `decision: "error"`, nothing signed. Test in Task 8.
- `audit.jsonl` hand-edited or a line deleted: `log --verify` names the first bad line; `spend.per_day` then denies with reason "audit log is broken at line N" instead of trusting it. Test in Task 6.
- A window that wraps midnight (`from 22:00 to 02:00`) checked at 01:00 on Saturday with `days` mon-fri: the window belongs to the day it started (Friday), so it's inside. Test in Task 5.
- The policy changed between `check` and `send`: `send` judges with the policy as it is now and logs its hash. Test in Task 9.

### Task 4: Reading the trace

**Files:**
- Create: `16-bouncer/src/trace.ts`, `16-bouncer/src/trace.test.ts`

**Interfaces:**
- Consumes: `Frame`, `TraceLog` (Task 1).
- Produces:
  - `type Hop = { address: Address; depth: number; path: Address[]; type: string; reverted: boolean }`
  - `type Facts = { reverted: { reason: string } | null; hops: Hop[]; prosOut: bigint; prosTo: Array<{ to: Address; amount: bigint; hop: Hop }>; tokensOut: Map<Address, bigint>; tokenTo: Array<{ token: Address; to: Address; amount: bigint }>; approvals: Array<{ token: Address; spender: Address; amount: bigint | "all" | "nft"; kind: "erc20" | "erc721" | "forall" }> }`
  - `readTrace(root: Frame, wallet: Address): Facts`
  - `explainRevert(output?: Hex): string` (copy 15-onego `check.ts`)
- Rules for `readTrace` (from the spec): hops = CALL, CALLCODE, CREATE, CREATE2 frames at every depth, including frames under a reverted subtree (`reverted: true`); STATICCALL and DELEGATECALL are not hops; precompiles `0x…01` to `0x…11` are skipped; `path` runs from the wallet to the hop. PROS out = `value` of non-DELEGATECALL, non-STATICCALL frames with `from` = wallet that did not revert. Token out = Transfer logs (3 topics) from the wallet, in frames that did not revert. Approvals: Approval with 3 topics (erc20, amount from data), Approval with 4 topics (erc721), ApprovalForAll with data true (forall), owner = wallet. `reverted` = top frame `error`, reason from `explainRevert(output)`.
- [ ] **Step 1: Write failing tests**:
  - `pMusk buy shows the hidden hops` (tape `pmusk-buy.json`): hops include the market at depth 0 and `0x30bebe…bb56` at depth 1 with `path` `[wallet, market, 0x30be…]`; `prosOut === 1000000000000000n` (the DELEGATECALL copy of the value is not counted twice).
  - `PROS send`: `prosTo` has `0x…dEaD` with 0.001 PROS; the only hop is the top frame to `0x…dEaD` (no code, so `contracts` will skip it).
  - `max approve`: one erc20 approval to the router with `amount === maxUint256`.
  - `too big buy`: `reverted` is set with a readable reason.
  - Synthetic frames: a Transfer inside a reverted child is not counted; a STATICCALL to an unknown contract is not a hop; a CREATE frame is a hop.
- [ ] **Step 2: Run tests.** Expected: FAIL.
- [ ] **Step 3: Implement `trace.ts`.**

### Task 5: The rules

**Files:**
- Create: `16-bouncer/src/rules.ts`, `16-bouncer/src/rules.test.ts`

**Interfaces:**
- Consumes: `Policy` (Task 3), `Facts`, `Hop` (Task 4).
- Produces:
  - `type RuleId = "policy" | "time_window" | "simulation" | "contracts" | "recipients" | "approvals" | "spend.per_tx" | "spend.per_day"`
  - `type Check = { rule: RuleId; ok: boolean; reason: string; hop?: Hop }`
  - `type Situation = { policy: Policy; now: Date; facts: Facts | null; hasCode: (a: Address) => boolean; balance: bigint; worstGas: bigint; spentToday: Map<string, bigint> | { broken: string } }` (spend keys are the policy's spend keys: `"PROS"` or the token's key)
  - `checkTimeWindow(s): Check`, `checkSimulation(s): Check`, `checkContracts(s): Check`, `checkRecipients(s): Check`, `checkApprovals(s): Check`, `checkSpendPerTx(s): Check`, `checkSpendPerDay(s): Check`
  - `judge(s: Situation): { decision: "allow" | "deny"; rule: RuleId | null; reason: string; checks: Check[] }`: runs them in order, stops at the first failure; on allow, `rule` is null and `checks` has all seven.
- Specifics: `time_window` absent from the policy = passes with reason "no window set". Wrap-around windows belong to the day they start. `simulation` fails on `facts.reverted` or on `value + worstGas > balance`. `contracts` fails on the first hop with code not on `contracts` (CREATE always fails: "creates a new contract"); reason names the address, depth and path. `recipients`: PROS to an address without code and every token receiver must be the wallet, on `recipients` or on `contracts`. `approvals` per the spec. `spend.per_tx`: any asset leaving the wallet with no `spend` entry fails ("no limit set for <token>, so none may leave"). `spend.per_day` fails on `{ broken }` with that reason, or when today + this > perDay; reason shows both numbers in whole units.
